  <action>
    Créer `plugin/_internal/lib/vf-portable.sh`. C'est une lib SOURCÉE : pas de `set -e`, pas
    d'effet de bord à l'inclusion autre que la définition des symboles et de la détection Windows,
    aucune écriture, aucun `exit`. En-tête en français, densité et ton du dépôt, citant ADR-054 pour
    justifier chaque choix de robustesse.

    **Détection Windows** — variable positionnée INCONDITIONNELLEMENT au chargement (donc sûre sous
    `set -u` chez le consommateur), dérivée du nom de système et de la variable d'environnement
    système. Documenter qu'un consommateur ne doit jamais la redéfinir.

    **Les 5 symboles du contrat :**
    - `vf_py_probe <candidat> [--fast]` — sonde un candidat : présent, chemin ne relevant pas du
      stub du magasin d'applications Windows, exécutable réellement (sonde d'exécution gardée par
      une temporisation là où elle existe), et bien un Python 3. Le drapeau `--fast` limite la sonde
      aux contrôles de PRÉSENCE et de CHEMIN, sans sonde d'exécution : c'est le profil « zéro spawn
      ajouté » de l'amendement ADR-054 point 3, indispensable pour une garde qui tourne à CHAQUE
      édition de fichier. Documenter les deux profils dans l'en-tête et dire lequel s'emploie quand.
      C'est la résolution explicite de l'hypothèse A1 de la recherche : le contrat ne tranche pas la
      fréquence d'appel, la lib expose donc les deux profils au lieu d'en deviner un.
    - `vf_resolve_python [--fast]` — cascade `python3`, puis `python`, puis le lanceur à argument
      Windows, en propageant le drapeau à la sonde. Mémorise le résultat dans des variables de
      processus pour ne pas re-sonder à chaque appel. Rend non nul si aucun candidat ne passe, sans
      rien imprimer (c'est l'appelant qui décide du message et du code).
    - `vf_python <args…>` — **fonction, pas variable** : elle INVOQUE l'interpréteur résolu, en
      insérant l'éventuel argument du lanceur avant les arguments reçus. C'est ce qui fait du
      lanceur à argument un barreau de plein droit, ce qu'une variable de chemin ne peut pas porter.
      Résout paresseusement si la résolution n'a pas encore eu lieu.
    - `jqx <args…>` — enveloppe de `jq` qui neutralise le retour chariot du `jq` natif Windows.
      Reprendre l'idiome exact déjà en production dans le dépôt (5 définitions identiques, aucune
      dans le périmètre dev : la lib les remplacera un jour, elle ne les touche pas ici).
    - `vf_guard_unavailable <script> <motif>` — les trois actions du contrat §4, ensemble : écrire
      une ligne (horodatage au format ISO, nom du script, motif) dans un fichier de marqueur nommé
      d'après le script, sous le répertoire de santé des gardes (variable d'environnement dédiée,
      avec un défaut sous le cache utilisateur si elle n'est pas posée) ; imprimer le motif sur
      stderr préfixé par le nom du script ; et RENDRE le code que l'appelant doit utiliser pour
      sortir. Ce code est non nul et **différent de 2** (D-02) : sur une garde `PreToolUse`, 2
      bloquerait toute édition tant que Python manque, alors que la doctrine est « dégradé mais
      utilisable » (ADR-031). La fonction ne sort jamais elle-même — c'est l'appelant qui sort avec
      la valeur rendue. Écriture du marqueur atomique (fichier temporaire puis renommage) et
      totalement fail-safe : si le répertoire n'est pas créable, la fonction imprime quand même le
      motif et rend le même code, elle ne casse jamais l'appelant.

    **Le bloc localisateur** — définir, dans l'en-tête de la lib, le bloc CANONIQUE à recopier chez
    les consommateurs, encadré par les deux lignes de marqueur ouvrant et fermant du contrat §3
    (les reprendre au caractère près depuis le contrat). Le bloc essaie les 4 candidats dans
    l'ordre du contrat (installation à plat, engine dans le cache, module ou installeur dans le
    dépôt, extracteur copié) ; aucun candidat trouvé ⇒ message préfixé sur stderr et sortie non
    nulle, jamais un `source` muet. Le SEUL jeton qui varie d'un consommateur à l'autre est le
    préfixe de message.

    Puis créer `plugin/_internal/tests/test-vf-portable.sh` (convention de suite du dépôt, isolation
    `mktemp`, `ok()`/`ko()`), avec au minimum : chargement de la lib sous `set -u` sans erreur ; les
    5 symboles définis après chargement ; la fonction d'invocation exécute réellement un programme
    Python trivial ; un candidat stub simulé (chemin ressemblant au magasin d'applications Windows,
    monté sur un PATH de test) est REJETÉ par la sonde ; le profil rapide ne lance AUCUN processus
    (prouvé par un compteur de shim) ; le marqueur est écrit, le motif part sur stderr, et le code
    rendu est non nul et différent de 2 ; répertoire de marqueurs non créable ⇒ le motif est quand
    même imprimé et le code rendu est le même. Trois issues par cas, jamais un skip silencieux.
    Mutations à jouer et à citer dans le SUMMARY : (m1) retirer l'exclusion du stub ⇒ le cas du stub
    devient rouge ; (m2) faire rendre 0 à la fonction de marqueur ⇒ le cas de code devient rouge ;
    (m3) faire lancer un processus au profil rapide ⇒ le cas du compteur devient rouge.
