## Critères PASS / FAIL — écrits à l'avance, avant toute observation

> Ces critères sont figés par ce plan. Ils ne se renégocient pas au vu du résultat.

**PASS — les trois conditions, toutes vérifiées :**

1. L'échelle des 7 gates résout `backend: "workflow"` avec une version de SDK **réellement
   installée** et lue dans le `package.json` du paquet — jamais un drapeau inventé.
2. Le run réel trivial (étape 2) produit les mêmes artefacts que le chemin inline : les deux fichiers
   attendus existent, chacun dans le commit de son propre worker, aucune collision, run terminé sans
   intervention humaine.
3. La sous-expérience de la Décision A confirme que l'absence d'entrée utilisateur en cours de run
   **ne produit pas de silence dangereux** : soit le run échoue explicitement, soit il remonte le
   besoin dans son rapport de fin de run. Jamais un « faux terminé » qui aurait ignoré la demande.

**FAIL — n'importe laquelle de ces conditions :**

1. L'échelle ne résout jamais `workflow`, même avec un SDK installé et la capability activée
   (blocage structurel du poste ou du runtime). **Ce critère couvre nommément le cas où aucune des
   options de persistance de `GSD_AGENT_SDK_VERSION` (section « Où persiste `GSD_AGENT_SDK_VERSION`
   au runtime » ci-dessous) n'est jugée acceptable pour ce poste** — corrigé suite à revue, B1 :
   sans persistance retenue, l'échelle ne résout `workflow` que lorsqu'un drapeau manuel est repassé
   à la main à chaque run, ce qui *est* le blocage structurel visé ici, pas une exception à part.
2. Le run réel diverge du chemin inline : artefacts différents, erreur non récupérée, worktree non
   nettoyé.
3. La sous-expérience de la Décision A révèle un silence dangereux — le run se termine en succès
   alors que la question posée par l'agent n'a été traitée nulle part, ni dans le rapport, ni
   ailleurs.

**Sur FAIL** : le livrable se conclut par un **refus motivé et écrit**, sur le patron des capacités
dormantes refusées en Phase 24 (GSDA-06, GSDA-08, GSDA-10), avec son déclencheur objectif de
reprise — jamais un abandon silencieux, jamais une config laissée à demi activée.

**Sur PASS partiel** (échelle franchie mais Décision A incertaine) : l'activation reste possible
**uniquement** si la décision écrite pose le repli « un étage = un workflow » en contrainte
opérationnelle du manager — jamais un workflow multi-étages sans point d'arbitrage humain entre eux
(D-02).

## Où persiste `GSD_AGENT_SDK_VERSION` au runtime — options et coûts (B1, correction de revue)

**Le problème que cette section ferme.** La tâche 1 établit la version du SDK honnêtement — paquet
réellement installé, valeur réellement lue dans son `package.json` — mais dans un répertoire
**jetable**, supprimé aussitôt après lecture. Le code amont
(`claude-orchestration-command-router.cjs`, fonction `resolveInstalledAgentSdkVersion`) résout la
version, dans l'ordre, par : un drapeau explicite `--agent-sdk-version` · la variable
`GSD_AGENT_SDK_VERSION` · une remontée de `node_modules` depuis le `cwd` de l'appelant **et** depuis
le `__dirname` du router lui-même (c'est-à-dire depuis l'arborescence de `gsd-core`). Or
`resolve-wave-dispatch` — la commande que `execute-phase.md` invoque réellement en production, pas
`detect-backend` — **ne reçoit plus le drapeau** depuis 2026 (#2590 : « `--agent-sdk-version` n'est
plus passé ici, le router résout lui-même la version installée »). Sur ce poste, aucune des deux
chaînes de remontée ne trouve le paquet : ni `cwd` (la racine de ce dépôt, qui n'a et ne doit avoir
aucun `node_modules`), ni `__dirname` (l'arborescence de `gsd-core` sous `~/.claude`, qui n'a
aujourd'hui aucun `node_modules` non plus). **Sans un geste de persistance délibéré, le gate n°5 rend
`agent_sdk_version_unknown` à chaque run réel de production**, quel que soit le verdict du spike.

Trois options existent, avec des coûts et une portée différents — aucune n'est neutre, c'est
pourquoi ce choix revient à Samuel au checkpoint de la tâche 2, pas à ce plan :

| # | Mécanisme | Portée | Coût / risque |
|---|---|---|---|
| 1 | `GSD_AGENT_SDK_VERSION` dans le bloc `env` d'un `settings.json` de Claude Code (`.claude/settings.local.json` du lab, ou `~/.claude/settings.json` du poste) | Le lab seul (fichier local) ou tout le poste (fichier global), selon le fichier choisi | Valeur figée à la main, aucune mise à jour automatique si le SDK est republié — **dérive silencieuse** : le gate 5 continuerait de résoudre une version obsolète sans avertir personne. Ne touche aucun `package.json` |
| 2 | `export GSD_AGENT_SDK_VERSION=…` dans le profil shell du poste (`~/.zshrc`/`~/.bashrc`) | Toute session shell du poste, hors du contrôle git de ce dépôt et non partageable entre postes d'une équipe | Même dérive silencieuse que l'option 1, avec une portée encore plus large et moins traçable (pas de fichier suivi, même localement) |
| 3 | Installation **réelle et persistante** du paquet quelque part sur la chaîne de résolution empruntée par `resolveInstalledAgentSdkVersion` — jamais à la racine de ce dépôt (interdit par T-27-05-SC et par l'absence volontaire de `package.json` racine), mais possible un cran plus haut dans l'arborescence de `gsd-core` (ex. `~/.claude/node_modules/@anthropic-ai/claude-agent-sdk`, sur la chaîne remontée depuis `__dirname`) | Tout le poste, toutes les missions et tous les labs qui invoquent ce même `~/.claude/gsd-core` | Une dépendance npm réelle à tenir à jour sur la machine, hors du contrôle git de **ce** dépôt — exactement le geste que T-27-05-SC refuse **au niveau du dépôt**, mais qui redevient possible **au niveau machine**, avec la responsabilité de maintenance que cela implique |

**Aucune de ces trois options n'est posée par ce plan.** C'est un réglage qui engage le poste bien
au-delà de cette phase, au même titre que `worktree.baseRef` (D-03, plan `27-03`) — la tâche 2
(checkpoint) le rend explicite et le tranche avec Samuel, jamais en silence.
