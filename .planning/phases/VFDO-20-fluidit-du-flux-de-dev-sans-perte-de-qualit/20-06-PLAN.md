<assumption_delta_decision>
**Transition détectée** : la revue passe d'un cas PARTICULIER (un nœud posé à la main dans le seul
protocole d'étages croisés dev ↔ design) à un cas GÉNÉRAL (un nœud posé systématiquement pour toute
étape de toute mission de dev). C'est une généralisation d'hypothèse : le singulier devient pluriel,
et le conditionnel devient systématique.

**Nom qui devient primaire** : le nœud de revue du plan de bataille, dépendant du nœud d'exécution
correspondant, tel qu'il est déjà écrit dans le protocole d'étages croisés. Il cesse d'être la
déclinaison design d'un cas particulier pour devenir LE patron général de l'étage revue.

**Décision : `promote`.** Le patron déjà écrit pour l'étage croisé devient le patron général ; le cas
croisé en devient une INSTANCE, pas une exception. Concrètement, la doctrine générale est écrite
dans le fichier de protocole de mission, et le fichier d'étages croisés continue de la spécialiser
sans la dupliquer — il n'est pas modifié par ce plan.

**Rationale (une ligne)** : le cas existait déjà, écrit et éprouvé, pour l'étage design croisé —
généraliser un patron éprouvé coûte moins et ment moins que d'inventer un second mécanisme parallèle
pour le cas nominal.
</assumption_delta_decision>

Deux fichiers, deux gestes de nature différente : le DÉTAIL va dans le fichier de référence, le
manager n'en garde que ce qu'il doit savoir sans le charger — c'est la contrainte de densité qui

**Dans le fichier de référence de protocole**, ajouter une section d'étage revue, numérotée à la
suite des patrons existants et placée après le patron de rapport typé, avant le renvoi aux étages
croisés. Elle couvre cinq points, dans cet ordre.

1. *Pose du nœud.* Pour chaque étape, le manager pose un nœud de revue dépendant du nœud d'exécution
   de la même étape, avec la même forme de commande que celle déjà écrite dans le protocole d'étages
   croisés — la citer, ne pas la réinventer. Le nœud est posé SYSTÉMATIQUEMENT, au même titre que le
   test et l'audit sont posés quand ils s'appliquent. Le périmètre de chaque nœud est déclaré avec
   le flag livré par le plan de kernel : c'est ce qui rend calculable le critère de fichier partagé,
   et sans déclaration ce critère est aveugle — le dire explicitement.

2. *Dispatch et boucle.* Le relecteur est dispatché DIRECTEMENT par le manager, jamais via l'agent
   d'exécution. Sur un rapport typé signalant des manques, le manager rouvre le nœud de revue puis
   dispatche l'agent d'exécution sur un mandat de CORRECTION CIBLÉE — les findings, et rien d'autre
   — jamais un cycle complet. Puis il re-dispatche le relecteur. Budget de trois tours ; au-delà,
   escalade, jamais de raffinage infini. Articuler explicitement cette boucle sur la table de
   pilotage déterministe par statut déjà écrite dans le corps du manager, pour qu'il n'y ait pas
   deux règles concurrentes.

3. *Gradation par risque, jamais par volume.* Énumérer les quatre déclencheurs objectifs de revue
   renforcée : un adaptateur d'infrastructure non couvert par les tests ; un fichier partagé avec
   une mission parallèle en vol ; du code que la mutation ne couvre pas ; un geste utilisateur ou
   une géométrie de vue. Chacun est un FAIT constatable sur le différentiel ou sur le plan de
   bataille, pas une appréciation. Dire ce qui peut être allégé, et rien d'autre : domaine pur à
   mutation verte, documentation, catalogues sans ajout de clé. Poser la règle de défaut : dans le
   doute, revue pleine — le classement du lot est un point de décision, donc un point d'erreur, et
   le défaut doit être le sûr. Nommer explicitement le mauvais axe qu'on abandonne : la seule
