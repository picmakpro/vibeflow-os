## Correction du 2026-08-18 (post-exécution) — A-18-06 rouvert sur mesure, précédence changée

**Ce que ce plan écrivait initialement (ci-dessous, conservé pour l'historique) reconnaissait
uniquement les jetons littéraux `Complete` et `Livré v` côté garantie, `Pending` étant le repli
voyage implicite.** Rejoué sur l'archive RÉELLE `agentique-v1.0-REQUIREMENTS.md` (136 IDs), ce
contrat classait `code 3` (forme non reconnue, jamais écrite dans le fichier reconstitué) **86 IDs
sur 136 (63 %)** — tous des items cochés `[x]`, dont la traçabilité porte `Done — <détail>`,
`Planned — plan NN`, ou de la prose libre. **`Pending` n'apparaît nulle part dans le corpus réel.**
Un ID caduc absent est visible et corrigible ; un ID classé « forme non reconnue » et jamais écrit
est **invisible** — c'est exactement le mode de perte que cette phase existe pour empêcher,
reproduit à l'intérieur de son propre remède.

**Contrat retenu (implémenté, verbatim dans `requirements-survival-detect.sh`)** : la CASE À
COCHER devient le signal PRIMAIRE, binaire et falsifiable (même principe que le diff d'IDs du plan
18-01) — le texte de traçabilité n'est plus lu pour cette décision :
1. CADUQUE (code 2) — jeton `caduc` sur le corps OU la traçabilité, précédence absolue.
2. GARANTIE (code 0) — case cochée `[x]`, non caduque. Peu importe le texte de traçabilité.
3. VOYAGE (code 1) — case non cochée (`[ ]`/`[~]`), non caduque.
4. FORME NON RECONNUE (code 3) — repli STRICT pour les lignes sans case reconnaissable ; l'absence
   de ligne de traçabilité n'y contribue plus (elle ne pèse que sur la détection `caduc`).

Rejoué avec ce contrat : 134 garanties + 1 voyage + 1 caduque = 136/136, **zéro perte**. D-18-13
(zéro normalisation) tient à l'identique : la ligne écrite reste la ligne SOURCE verbatim, seul le
CODE de décision change, jamais le texte imprimé.

| Code | Destin | Condition de reconnaissance |
|---|---|---|
| 0 | Garantie | Case cochée `[x]` **ET** le texte de traçabilité contient `Complete`, ou le texte du corps contient le jeton littéral `Livré v` **sans** `caduc` sur la même ligne |

| 3 | Forme non reconnue | Ni 0, ni 1, ni 2 — la ligne ne correspond à aucun patron connu (inclut l'absence de ligne de traçabilité correspondante : l'appelant passe alors une chaîne vide en second argument, ce qui retombe naturellement ici, jamais un crash ni un abandon) |

**Correction mesurée le 2026-08-18, sur le rejeu réel (voir la tâche de rejeu du plan)** : la
condition 2 porte désormais sur les DEUX lignes, pas la seule ligne de corps. Sur l'archive réelle
`agentique-v1.0-REQUIREMENTS.md`, le jeton `caduc` de `VERB-02` vit **uniquement** dans sa ligne de
traçabilité (`| VERB-02 | Phase 12 | Livré v2.31.0 (17/18 verbes) — **caduc depuis v2.33.0** … |`,
l. 749) — sa ligne de corps (l. 148, `- [~] **VERB-02** *(partiel — 17/18, ...)*: ...`) ne porte

(cas 1, case `[~]` non cochée, aucun `caduc` sur le corps) et non en caduque — l'exact contraire de
l'exemple que ce document cite lui-même pour justifier la règle. La glose « Livré v2.31.0 … — caduc
depuis v2.33.0 » citée juste en dessous décrit la ligne de **traçabilité**, pas le corps : l'exemple
et la règle d'origine se contredisaient déjà avant cette correction.

L'ordre de test est figé : **caduque d'abord** (le jeton `caduc` gagne toujours, sur l'une ou
l'autre ligne, y compris sur une case cochée — c'est exactement `VERB-02`, dont la traçabilité porte
« Livré v2.31.0 … — caduc depuis v2.33.0 », qui doit sortir 2 et jamais 0 ni 1), puis garantie, puis
voyage, puis 3 en repli. Écrire cet ordre en commentaire au-dessus de la fonction : c'est le seul
endroit où la précédence est décidée.

**Zéro normalisation (D-18-13)** : la fonction ne réécrit JAMAIS le texte du statut. Elle ne fait
que trancher un code de destin ; la ligne écrite dans le fichier reconstitué est la ligne SOURCE,

**Cas 3 n'est jamais un abandon silencieux** : le script principal compte les lignes classées en
code 3 et les signale sur stderr avec leur ID si extractible (jamais bloquant, D-18-10 étendu par
analogie — le rattrapage aussi est lecteur, pas juge, sur ce qu'il ne reconnaît pas).

## A-18-07 — Construction du fichier reconstitué : ordre et sections figés

Dans cet ordre, du haut vers le bas :

1. Frontmatter/titre repris VERBATIM du fichier `REQUIREMENTS.md` **vivant actuel** si un fragment
   subsiste (titre `# Requirements: …`, ligne `**Defined:** …`) — sinon repris de l'archive. Le
   script ne fabrique jamais un titre de zéro.
2. Un bloc de préambule daté, format libre mais portant littéralement : jalon d'origine, date de
   reconstitution, chemin de l'archive source — sur le modèle du bloc `> **Clôture agentique-v1.0
   …**` déjà présent en tête du fichier réel (à lire comme référence de ton, pas à copier mot pour
   mot).
3. **`## Garanties`** (A-18-04 du plan 18-01) — une ligne par exigence classée code 0, verbatim, la
   case gardée `[x]`, triée dans l'ordre d'apparition de l'archive (jamais retriée par famille : la
   trace de qui a livré quoi appartenait déjà à cet ordre).
4. Les familles du corps **non-livrées** de l'archive, structure `### <famille>` reprise
   verbatim, ne contenant QUE les lignes classées code 1 (voyage), chaque ligne recevant le suffixe
   ` — carried-from: <jalon>` (D-18-12, une espace avant le tiret cadratin existant si la ligne en a
   déjà un, sinon directement en fin de ligne) où `<jalon>` est le libellé du jalon d'origine
   résolu par `vf_ledger_state` (`VF_LEDGER_MILESTONE`, déjà assaini par la liste blanche T-18-01
   du plan 18-01 — jamais une seconde extraction), écrit **verbatim, jamais préfixé d'un `v`
   fabriqué** — sur ce dépôt : `carried-from: agentique-v1.0`, pas `carried-from: vagentique-v1.0`.
   **Précision (levée le 2026-08-18, propagée depuis 18-01-PLAN.md D-18-12)** : le gabarit amont
   `v[X.Y]` est un **placeholder** pour « identifiant du jalon », pas un format de valeur imposé —
   l'amont ne se prononce que sur l'emplacement (colonne dédiée), jamais sur la forme de
   l'étiquette. Aucune ambiguïté avec `VF_LEDGER_MILESTONE` : c'est la MÊME valeur, verbatim.
5. `## Out of Scope` — reprise verbatim de l'archive SI présente, sinon omise (ne jamais fabriquer
   une section vide).
6. `## Traceability` — reconstruite avec UNIQUEMENT les lignes des exigences code 1 (voyage), la
   colonne Status inchangée verbatim. Les exigences code 0 et code 2 n'y figurent PAS — c'est la
   preuve sur pièce de D-18-03 (la table de traçabilité ne redevient jamais une liste de restes ET
   de garanties mélangées).
7. Pied de page daté, une ligne `*Reconstitué depuis l'archive <chemin> le <date> par
   restore-requirements-ledger.sh (LEDG-01).*` — la seule ligne qui identifie l'outil, pour qu'un
   futur agent qui lit le fichier sache d'où vient cette forme.

Les exigences code 2 (caduques) et code 3 (non reconnues) ne sont écrites NULLE PART dans le
fichier reconstitué — elles restent uniquement dans l'archive, exactement la doctrine D-18-11 pour
les caduques et un repli conservateur pour le non-reconnu (ne pas écrire ce qu'on n'a pas su
classer plutôt que de deviner).
