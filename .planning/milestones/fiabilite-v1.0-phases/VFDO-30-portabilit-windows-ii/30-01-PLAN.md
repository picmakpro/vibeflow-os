UNE seule entrée. Le moteur d'install (`merge-hooks.sh`) apprend la forme exec — substitution dans
`args`, propriété, dédup cross-forme, `remove` — et apprend à résoudre le chemin absolu de `bash`

fragment, puis le retire.

entrée, pas de `|| true`, donc aucune dépendance au lot des codes de sortie.

si la forme exec se révèle une impasse, elle est découverte après un commit, pas après dix.

  <action>
    Cinq modifications dans `merge-hooks.sh`, puis la migration d'une entrée. Ordre imposé : le
    moteur d'abord, le fragment ensuite, jamais l'inverse.

    (1) **Résolution du chemin absolu de bash, côté shell.** Ajouter une fonction
    `resolve_bash_abs()` avant l'appel du bloc Python. Cascade, dans cet ordre : la variable
    d'environnement `VF_BASH_BIN` (surcharge réservée aux tests, même convention que `BASH_BIN`
    dans `test-windows-guards.sh`) ; puis `$BASH`, le chemin de l'interpréteur qui exécute déjà ce
    script — source la plus fiable car elle ne passe par aucune recherche PATH ; puis le résultat de
    `command -v bash`. Un candidat n'est retenu que s'il commence par `/`, existe, est un fichier
    régulier et est exécutable — un candidat relatif est REJETÉ sans repli déguisé (c'est le motif
    de confinement de chemin fermé en Phase 27, ADR-070 : une acceptation borne le vecteur qu'elle
    couvre, jamais le risque en bloc). Exporter le résultat vers le bloc Python via une variable
    d'environnement `BASH_ABS`, aux côtés de `MODE`/`FRAGMENT`/`SETTINGS`/`PREFIX`.

    (2) **Substitution.** Côté Python, à l'endroit où `resolved["command"]` est calculé :
    substituer le jeton de chemin de scripts dans `command` ET dans chaque élément de la liste
    `args` (chaîne par chaîne, en ignorant tout élément non-chaîne sans planter) ; substituer le
    jeton de bash dans `command` uniquement. Le nom du jeton de bash est `VF_BASH` avec la même
    grammaire de délimiteurs doubles-accolades que le jeton de chemin de scripts existant. Après
    substitution, si une accolade double subsiste dans `command` ou dans un élément d'`args`,
    appeler `die()` avec un message nommant le fragment et l'entrée — le moteur refuse d'écrire un
    hook mort plutôt que de l'écrire silencieusement (spec §6 critère 4). Cas particulier : si le
    jeton de bash est présent mais que `BASH_ABS` est vide, `die()` avec un message qui dit quoi
    faire (installer bash / renseigner `VF_BASH_BIN`).

    (3) **`frag_basenames()`.** Ajouter la lecture de `h.get("args", [])` : appliquer `SCRIPT_RE`
    à chaque élément chaîne, en plus de `command`. Sans ça, un fragment 100% exec ne référence
    aucun basename et le mode `remove` meurt sur « fragment sans script référencé » — le module
    devient non désinstallable (spec §1.3 effet 3, déjà vérifié dans le code actuel).

    (4) **`references()`.** Étendre à `args` sans toucher au motif existant : le lookaround négatif
    reste EXACTEMENT le même, appliqué successivement à `command` puis à chaque élément chaîne
    d'`args`. Ne pas concaténer les éléments en une seule chaîne, ne pas remplacer la regex par une
    égalité de basename : la frontière fermée par lookaround est une régression prouvée
    (`archive.sh` ne doit pas matcher `gsd-archive.sh`) et elle doit rester la seule mécanique.

    (5) **Propriété et dédup.** Deux autres sites lisent `command` seul et doivent lire
    `command` + `args` : le calcul de `frag_names` qui décide si un groupe existant est
    entièrement possédé par VF (l.150-154), et le calcul d'`own` juste après la substitution
    (l.168). Sans (5), la dédup cross-forme ne purge pas l'ancienne entrée shell et le hook
    s'exécute deux fois.

    (6) **Migration de l'entrée.** Dans `plugin/software-architecture/hooks/hooks.json`, passer
    l'unique entrée `PreToolUse`/`Edit|Write` en forme exec : `type` reste `command` ; `command`
    devient le jeton de bash ; `args` porte le chemin du script (jeton de chemin de scripts +
    `/guard-file-size.sh`) comme unique élément. Mettre à jour la clé `description` du fragment
    pour dire que l'entrée est en forme exec et qu'elle est **bloquante** (elle rend un
    `permissionDecision: deny` en JSON — c'est sa décision JSON qui bloque, pas son code de
    sortie ; RESEARCH Pitfall 4). Ne toucher à aucun autre `hooks.json`.

    Ne pas modifier le bloc de résolution Python de `merge-hooks.sh` (l.54-71) : son volet Python
    reste à la polarité gouvernance (spec §3.1), seul le volet hooks est porté ici.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| fragment `hooks.json` → moteur | Le fragment vient du cache du plugin (source de confiance) mais est du JSON parsé sans schéma. |
| `settings.json` de l'utilisateur → moteur | Entrée NON maîtrisée : peut être corrompue, hostile, ou porter des entrées tierces à ne jamais toucher. |
| environnement d'install (PATH, `$BASH`) → `command` écrit | Le chemin résolu à l'install est figé dans un fichier exécuté à chaque hook. |
