# Plan 11-04 — Cohabitation settings.json (correctif merge-hooks + suite dédiée)

## But

Appliquer le correctif préventif spécifié en Phase 10 (dry-run réel sur un settings.json sandbox
post-install gsd-core) : matching ancré aux frontières de chemin (au lieu d'un test de
sous-chaîne, qui laisserait `archive.sh` détruire à tort une entrée tierce `gsd-archive.sh`), et
fin de la réutilisation de groupes « mixtes » (un groupe `(event, matcher)` n'est réutilisé que
s'il est déjà 100% VF). Prouver la cohabitation par une suite dédiée contre une fixture
représentative d'un settings.json post-install gsd-core.

Complète une partie du critère de succès 3 du ROADMAP (GSDM-06, volet non-régression isolée —
ce plan couvre la cohabitation hooks, pas encore le dry-run 3 scopes qui est en 11-06). Quatrième
plan de la chaîne — dépend de 11-01/11-02/11-03 par construction du squelette figé (fichiers
disjoints : `plugin/_internal/` n'est touché par aucun des 3 plans précédents, aucune dépendance
de contenu réelle).

## Exigences couvertes

GSDM-06 (partiel — cohabitation hooks ; dry-run 3 scopes + idempotence globale + purge legacy en

## Tâches

### 1. `plugin/_internal/tests/fixtures/gsd-core-settings.json` (nouveau — fixture synthétique)

Créer un `settings.json` synthétique structurellement fidèle à un post-install gsd-core réel
(Phase 10, dry-run) : 15+ entrées `hooks` réparties sur au moins 3 événements (`PreToolUse`,
`PostToolUse`, `Stop`), une `statusLine`, un bloc `permissions`. Inclure explicitement au moins :
- une entrée référençant un script `gsd-archive.sh` (event `Stop` ou équivalent) — c'est le cas
  discriminant pour T5 ;
- un groupe `(event, matcher)` déjà 100% GSD (aucun hook VF dedans) sur un matcher que VibeFlow
  utilise aussi par ailleurs (ex. `PreToolUse` matcher `Read`) — c'est le cas discriminant pour T4
  (non-mixité : VF ne doit PAS s'y injecter, il doit créer son propre groupe).

Pas de données réelles de la machine de l'exécuteur — noms de scripts et commandes génériques
mais plausibles (`gsd-prompt-guard.sh`, `gsd-context-monitor.sh`, `gsd-archive.sh`, etc., cohérent
avec les gains gratuits listés en `10-SOLUTIONS.md` §3).

### 2. `plugin/_internal/merge-hooks.sh` — matching ancré

Remplacer `references()` (l.117-118) :
```python
def references(entry, basenames):
    return any(b in entry.get("command", "") for b in basenames)
```
par une version ancrée aux frontières de chemin/mot (un basename ne matche que précédé de `/`,
début de chaîne, espace ou guillemet, et suivi de fin de chaîne, espace, guillemet ou frontière de
mot — empêche `archive.sh` de matcher `gsd-archive.sh`) :
```python
def references(entry, basenames):
    cmd = entry.get("command", "")
    for b in basenames:
        pattern = r"(?:^|[\s'\"/])" + re.escape(b) + r"(?:$|[\s'\"])"
        if re.search(pattern, cmd):
            return True
    return False
```
(`re` est déjà importé en tête du bloc Python, l.74 — aucun nouvel import requis.)

### 3. `plugin/_internal/merge-hooks.sh` — fin de la co-location de groupes mixtes

Dans la boucle de merge (l.122-154), la recherche d'un groupe existant de même `matcher` (l.130-133)
réutilise aujourd'hui n'importe quel groupe trouvé, même s'il contient des hooks qui ne référencent
aucun script du fragment courant (donc potentiellement des hooks tiers/gsd-core). Ajouter une
vérification de possession avant de retenir `target` :
```python
            matcher = g.get("matcher")
            target = None
            for eg in ev:
                if isinstance(eg, dict) and eg.get("matcher") == matcher:
                    # Ne réutiliser un groupe existant que s'il est déjà ENTIÈREMENT possédé par
                    # VF (tous ses hooks référencent un script connu du fragment courant) — sinon
                    # créer un nouveau groupe plutôt que de mélanger avec des hooks tiers/gsd-core
                    # (neutralise : migration de scope qui déplace tout le groupe,
                    # cleanupOrphanedHooks qui supprime le groupe entier — Phase 10, dry-run).
                    existing_hooks = eg.get("hooks", []) or []
                    frag_names = set()
                    for gg in groups or []:
                        for hh in gg.get("hooks", []) or []:
                            frag_names.update(SCRIPT_RE.findall(hh.get("command", "")))
                    if existing_hooks and not all(references(h, frag_names) for h in existing_hooks):
                        continue  # groupe mixte — ne pas réutiliser, en chercher un autre / en créer un nouveau
                    target = eg
                    break
```
(Le reste de la boucle — création d'un nouveau groupe si `target is None`, ajout des hooks,
dédup cross-matcher — est **inchangé**.)

### 4. `plugin/_internal/tests/test-gsd-cohabitation.sh` (nouveau)

Suite dédiée, calquée sur le style de `test-merge-hooks.sh` (helpers `ok()`/`ko()`, `mktemp`,
comparaison JSON via `python3 -c`). 5 cas :

- **T1 — merge sans perte** : copier la fixture dans un `settings.json` temporaire, merger un
  fragment VF synthétique (2-3 hooks, matchers `PreToolUse`/`Stop`) par-dessus. Vérifier :
  l'ensemble des paires `(event, command)` `gsd-*` de la fixture d'origine est un sous-ensemble
  du résultat ; `statusLine` et `permissions` sont deep-equal à la fixture d'origine.
- **T2 — remove restaurateur** : après le merge de T1, appeler `merge-hooks.sh remove` avec le
  même fragment VF. Vérifier : le résultat est deep-equal à la fixture d'origine (JSON complet).
- **T3 — idempotence** : deux `merge` consécutifs du même fragment sur la fixture → le résultat du
  2e merge est deep-equal au résultat du 1er (aucun doublon).
- **T4 — non-mixité post-correctif** : merger un fragment VF avec un hook sur le matcher
  `PreToolUse`/`Read` (le matcher déjà 100% GSD dans la fixture, tâche 1). Vérifier : le groupe
  GSD d'origine reste inchangé (mêmes hooks, même ordre) ET un NOUVEAU groupe `PreToolUse`/`Read`
  distinct est apparu portant le hook VF (aucun mélange dans une seule entrée `hooks[]`).
- **T5 — anti-collision suffixe** : merger un fragment VF portant un hook
  `consolidator-archive.sh` (nom choisi pour partager le suffixe `archive.sh` avec l'entrée
  `gsd-archive.sh` de la fixture). Vérifier : après merge ET après remove de ce fragment, l'entrée
  `gsd-archive.sh` de la fixture est **toujours présente**, intacte (preuve directe que le
  matching ancré empêche la collision de suffixe).

## Risques / points d'attention

- **Ne pas casser `test-merge-hooks.sh` T7** (dédup cross-matcher à l'upgrade de matcher,
  l.169-171) — le correctif de non-mixité (tâche 3) ne doit s'appliquer qu'à la recherche d'un
  groupe **existant** à réutiliser, jamais à la logique de dédup cross-matcher qui parcourt déjà
  tous les groupes de l'événement (l.148-150, hors périmètre de ce correctif).
- **`frag_names` doit être calculé sur TOUT le fragment**, pas seulement le groupe courant `g` —
  sinon un fragment VF à plusieurs groupes pourrait se voir refuser un groupe qu'il possède déjà
  via un autre de ses propres groupes (faux négatif de possession).
- **La fixture n'est pas une copie de la machine réelle de l'exécuteur** — c'est une construction
  synthétique. Ne jamais copier un `settings.json` réel dans le repo (fuite potentielle de
  configuration locale).
- **Ce plan ne touche à aucun module versionné** (`_internal` n'a ni `VERSION` ni `module.json`) —
  son changement sera documenté dans le `CHANGELOG.md` **racine** en 11-06, pas ici.
