## Mesures qui fondent ce plan (2026-11-05)

- `vf-cockpit-server.mjs` l.70 répond 405 à toute méthode autre que GET sous `/api/vf/` ; l.103 répond 404 à tout GET inconnu. Le module ne change rien pour un chemin hors table (`reconnait` faux) : le comportement actuel est conservé par construction.
- `serve.mjs` l.508-514 contrôle le `Host` (127.0.0.1 ou localhost avec le port), accepte une `Origin` ABSENTE (`!req.headers.origin || …`) et un jeton soit global soit de page : trop permissif pour une route qui propose un lancement. Ce module refuse l'`Origin` absente et n'accepte que les jetons que l'appelant lui donne.
- Le jeton se lit dans l'en-tête `x-floorplan-token` en source (`vf-cockpit-server.mjs` l.108), renommé `x-vf-cockpit-token` dans la sortie par `renommerTexte` de `vf-cockpit-rename.mjs` (règle `floorplan` -> `vf-cockpit`, appliquée à tous les `vf-cockpit-*.mjs` copiés par le build).
- `egal(a, b)` de `vf-cockpit-terminal-amorce.mjs` condense les deux chaînes (SHA-256) puis `crypto.timingSafeEqual` ; tout type autre qu'une chaîne vaut faux. La suite de la Phase 71 prouve ce patron par une sonde statique (`TC`, `test-cockpit-terminal-serveur.sh` l.395-404) : elle est reprise ici, avec son témoin positif.
- Node répond lui-même 400 à une requête HTTP/1.1 sans `Host` tant que l'option `requireHostHeader` n'est pas désactivée : la suite désactive cette option sur SON serveur de test pour exercer le contrôle du module.
